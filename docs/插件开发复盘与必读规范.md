# 插件开发复盘与必读规范

> 本文是 `C:\sta\status-atelier` 的强制必读文件。每次开始本插件的开发、诊断、测试或发布前都必须重新阅读。

## 一、这次失败发生了什么

开场白主页先后出现了三种状态：

1. 裸 HTML 可以显示视觉界面，但其中的 `<script>` 不会执行，所以“进入”按钮看得见却没有反应。
2. 为了执行脚本，生成结果被改成 fenced HTML 代码块。
3. fenced HTML 中只放了 `<div>...</div>`，遗漏酒馆助手 iframe 渲染器要求的完整 `<body>...</body>`，因此又被当成普通代码块原样显示。

真正的必要条件并不是“用了代码块就能运行”，而是：

- 内容位于 fenced HTML 代码块中；
- 文档同时包含 `<body>` 与 `</body>`；
- 交互代码在 iframe 中执行，并通过 TavernHelper / SillyTavern 的真实接口操作消息；
- 生成后的正则作用楼层、查找规则和重新渲染行为与用户的实际环境一致。

## 二、我做错了什么

### 1. 把自己的推断写成了契约

第一次修复只验证“HTML 能显示”，没有验证 `<script>` 是否真的执行。第二次修复只验证“存在 fenced HTML”，没有验证酒馆助手识别 iframe 的完整条件。两次测试都在证明我刚写下的假设，而不是证明用户的实际路径能够工作。

### 2. 没有先完整对照能工作的参考正则

用户已经提供 `regex-开场白.json`。应该先比较以下真实字段和文档结构：

- `findRegex`
- `placement`
- `markdownOnly`
- `runOnEdit`
- `replaceString` 的开头、结尾和完整 HTML 外壳
- 按钮实际调用的 TavernHelper API

如果先完成这项对照，就会立刻发现参考文件拥有 `<!DOCTYPE html>`、`<html>`、`<body>` 和 `</body>`，而错误版本没有。

### 3. 混淆了静态通过与设备通过

Node 测试、语法检查和静态检查只能证明生成器与当前断言一致，不能证明 TauriTavern 手机上的渲染器已经接管代码块，也不能证明触摸按钮后真实切换了额外问候语。

以后必须明确区分：

- 静态检查通过；
- 生成物结构通过；
- 本地浏览器或模拟环境通过；
- SillyTavern / TauriTavern 真实运行通过；
- 用户设备验收通过。

没有哪一层可以冒充后一层。

### 4. 发布节奏太快

在关键运行契约仍靠推测时就连续提交，迫使用户反复更新和重新导入。这增加了用户的验证成本，也损害了对测试结果的信任。

## 三、今后必须执行的工作顺序

### 第 1 步：只读取当前问题相关部分

先用精确搜索定位：

- 当前插件的生成器、解析器、设置界面和对应测试；
- 用户提供的参考 JSON、截图或录像；
- 实际调用到的 SillyTavern / TavernHelper API；
- 官方文档中与该行为直接相关的一页或一节。

禁止先扫描整个酒馆工程。局部证据不足时才能扩大范围，并先说明原因。

### 第 2 步：把真实参考转成差异清单

不能只看视觉结果。需要逐项比较输入、正则字段、HTML 文档结构、运行环境、API 调用、索引规则和错误反馈。先找到最小差异，再修改代码。

### 第 3 步：先写能复现用户失败的回归检查

回归检查必须来自真实故障。例如这次至少要检查：

- fenced HTML 存在；
- `<body>` 和 `</body>` 同时存在；
- 成品 JSON 的 `placement` 与参考契约一致；
- 生成脚本语法有效；
- 按钮绑定真实切换 API；
- 四套生成包均满足同一契约。

测试不能只搜索一句新加的代码，也要检查最终导出的 JSON。

### 第 4 步：生成并检查最终成品

运行构建与测试后，还要直接读取生成物，至少核对：

- JSON 可以解析；
- `replaceString` 的头尾正确；
- 没有 `$1`、旧标签或空数据残留；
- HTML 文档闭合；
- 版本号一致；
- 旧正则是否需要用户删除、覆盖或重新导入。

### 第 5 步：如实报告验证边界

如果没有运行中的 TT/ST 客户端，就只能说静态与生成物检查通过。不得说“真实点击已经成功”。用户提供新的截图或录像后，应把它当成最高优先级证据重新诊断。

### 第 6 步：满足发布门槛后再提交

只有以下条件全部满足才能提交和推送：

- 修改范围明确且没有夹带无关文件；
- 相关测试全部通过；
- 最终生成物已检查；
- 版本与说明同步；
- 用户已经授权当前发布动作；
- 对尚未完成的设备验收作出明确说明。

## 四、插件优化管理原则

- 保留真实角色卡、世界书、额外问候语和用户已填写内容，不用伪造数据替代绑定。
- 通用功能必须对其他角色卡同样成立，不能只为单一卡片名称写死。
- 修复应针对生成与解析契约，不要求用户手工修改每一份导出文件。
- 旧版本成品不会自动变化时，必须明确告诉用户需要重新生成、覆盖或导入。
- 不输出、清空或改写用户的 API Key；测试日志不得暴露密钥。
- 作者署名统一使用“九一”。
- 主页标记、正则替换、样式模板、问候语切换和世界书绑定分别管理，避免一次修改破坏整条链路。
- 每次开始时先读取现状、版本、未提交修改和测试状态，不重做已经完成的内容。

## 五、这份复盘的结论

问题不在于“测试数量不够”，而在于测试是否覆盖真实运行契约。以后先读真实参考、只读相关代码、用用户故障建立回归检查，并把静态验证与设备验收严格分开。只有这样，测试通过才有意义。
